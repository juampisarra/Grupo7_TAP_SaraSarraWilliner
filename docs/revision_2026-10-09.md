## Problemas encontrados y alcance de las correcciones

- En `.venv` faltaban Gunicorn y WhiteNoise, aunque estaban declarados en `requirements.txt`. Se instalaron mediante `pip install -r requirements.txt`; luego `collectstatic` y la carga de estáticos funcionaron.
- El `.env` local real no incluía `DJANGO_SECRET_KEY`, `DJANGO_DEBUG` ni `DJANGO_ALLOWED_HOSTS`. Se agregaron una clave nueva para desarrollo, `True` y `localhost,127.0.0.1`, respectivamente. La clave permanece privada. Esto no cambia las variables del servicio en Render.
- La plantilla usa comprobaciones de verdadero/falso para dormitorios, precios y coordenadas. Un cero se interpreta como ausencia. No había publicaciones con cero dormitorios en la instantánea; la corrección de la plantilla sigue pendiente.
- `check --deploy`, simulando el entorno de Render con una clave temporal, detectó el backend de correo de consola como configuración de desarrollo y advertencias por HSTS y redirección HTTPS en Django. No hay funcionalidad de correo implementada. La redirección HTTP a HTTPS sí se comprobó en el servicio público. El check básico aprobado no equivale a aprobar todos los controles de despliegue.
- `MIDDLEWARE` está definido dos veces en `config/settings.py`. Python utiliza la segunda definición, que incluye WhiteNoise en el lugar esperado. Es una redundancia para limpiar, sin fallo observado.
- Las credenciales compartidas en el chat deben reemplazarse. No se modificó la contraseña de Supabase ni la clave del servicio desplegado.

No se modificó el código de la aplicación, no se escribieron datos en Supabase, no se ejecutó la ingesta ni se realizó un despliegue.

## Para qué sirve cada incorporación

| Componente | Función y estado |
| --- | --- |
| Django en Render | Atiende las visitas desde una URL pública, aunque las computadoras del equipo estén apagadas. Implementado. |
| Gunicorn | Ejecuta la aplicación Django como servidor en Render. Declarado en el comando de arranque documentado; no se probó su ejecución en Windows. |
| WhiteNoise y `collectstatic` | Reúnen y sirven CSS, JavaScript e imágenes estáticas, incluidos los del administrador. Implementado. |
| Variables de entorno | Separan credenciales y configuración del código. El entorno local y Render tienen sus propios valores. Implementado. |
| `DEBUG=False` | Evita mostrar detalles internos de errores a visitantes. Configurado para producción por defecto; las respuestas públicas observadas no mostraron trazas. No se inspeccionaron las variables del panel. |
| Hosts permitidos y proxy HTTPS | Admiten el dominio del sitio y permiten que Django reconozca HTTPS detrás de Render. Implementado. |
| PostgreSQL en Supabase y psycopg | Conservan los datos fuera del servidor web y permiten que Django y la ingesta compartan la base. Implementado. |
| Adaptador y flujo común de ingesta | Separan la extracción de Brega de la normalización y el guardado; actualizan por fuente e identificador. Implementados, ejecución manual. |
| Datos ampliados, precisión y caché | Guardan textos para la futura búsqueda, distinguen ubicaciones aproximadas y reutilizan consultas inversas de localidad. Implementados. |
| Elasticsearch en Elastic Cloud | Resolverá búsquedas de texto y ranking de relevancia. Pendiente. |
| PostGIS dentro de PostgreSQL | Resolverá filtros por radio y área. No está instalado en la base consultada ni integrado en el código. |
| GitHub Actions | Ejecutará la ingesta programada sin una computadora del equipo encendida. Pendiente. |
| cron-job.org y `/health/` | Harán solicitudes ligeras para reducir el reposo del servicio; no importarán propiedades. Ruta y configuración pendientes. |

Hoy el flujo es: **comando manual → Brega → normalización → Supabase**. Las visitas siguen **navegador → Django en Render → Supabase → HTML**. Cambiar los datos de la base no requiere desplegar otra vez el código.
